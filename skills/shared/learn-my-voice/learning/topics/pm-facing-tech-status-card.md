# 給 PM 看的技術狀態卡

## Scope
- Audience: 產品／專案負責人與跨職能團隊；懂業務、不一定懂實作。
- Document types: 知識庫（如 Notion）上的技術方案狀態卡、設計初版、決策摘要。

## Confirmed choices
- 提到資料庫概念時點出實際的表名／欄位名，不用抽象描述帶過。
- 每張卡只放該層／該模組自己的決策；共用或下游流程放在它真正發生的那一層，
  不因先寫到就塞進當前卡。
- 團隊還沒拍板的事不寫「已定案」，用「初版」「初版規劃」。
- 展開可見的正文只放有把握的內容；沒把握的標「不確定、之後解」或收進 toggle。
- 不把開放式問題丟給團隊；提出幾個具體方案（可附推薦）讓團隊選。
- 使用者在檔內用英文留技術問題時，要的是判斷＋直接改進正文，不是把問題原樣留著；
  能站內做的（既有 DB 內建能力）優先，外部服務往後推。
- 「之後再說」是正式段落，放已決定不做第一版的東西，各附一句理由。

## Working hypotheses
- 砍掉解釋性子句與非必要補充（例如「不是硬門檻」「沒有可調的後台旋鈕」），
  只留判斷需要的最少資訊。
- 中文名詞後括號附英文／程式識別字，例如「求助單(ticket)」；正文可混用英文名詞。
- 有疑問時直接在文件裡留白話問題與 cmiiw，期待懂業務的人糾正。

## Avoid
- 把英文術語硬翻成生僻中文（例：shadow mode 譯成「旁路測試」）；改用白話描述
  行為，並一次性附註英文原文。
